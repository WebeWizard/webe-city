# Public Information Writing

## Plugin loading and recovery

Before resolving plugin resources, follow [plugin loading and recovery](../../docs/plugin-loading.md).
Discover the exact installed path and host-listed activation identifier; resolve
links from the containing installed file, not the target repository or cwd.
Carry verified plugin/version, canonical records checkout and limits through
handoffs. Correct an observed path or syntax error once within existing tools
and authority; never repeat unchanged failures or bypass real blockers.

Use this method only in response to a resident's specific request under the
adopted public-information policy and appointment. It does not commission
work or grant permission to issue anything.

## Scope before drafting

1. Capture the resident's question or desired outcome. In a short brief, name
   the audience, purpose, format, source offices, what is excluded, and how
   reviewers will check the product. Ask what readers should understand or
   do next. Determine whether they want a standalone product or an actual
   repository change. Note any requested external release separately.
2. Stop at the brief until the Manager supplies a case-specific authorization
   and scoped assignment. Do not treat a routine documentation class, a
   draft decision, or the request itself as approval.

## Write and review

1. Collect only the sources needed for the brief. Use the canonical decision
   or service record for authoritative statements and confirm practical claims
   with the source office. Do not turn a proposal into a decision, an accepted
   change into a claim of live availability, or an estimate into a date.
2. Lead with the answer and its implications. Use descriptive headings, short
   sentences, concrete dates where known, and links that the intended audience
   may actually access. Explain unfamiliar terms. Name the responsible contact
   route when useful. Keep uncertainty and dissent visible where material.
3. Remove unnecessary personal information, restricted details, and private
   links not cleared for the audience. Do not put restricted originals in Git,
   a filing payload, or a public-facing draft. Return unresolved source or
   access questions to the Manager.
4. Mark the copy as a draft. Return it with the case, authorized brief and
   decision references, source list, and outstanding reviews. Obtain fact and
   classification review through the Manager; include the Clerk if it cites
   decisions. A correction is a new linked revision with a reason, not a
   silent overwrite of the prior accepted copy.

For example, scope an internal FAQ around three specific resident questions
and check each answer against the service owner's records; for a requested
public-facing guide, identify confirmed steps and permitted source links, then
return it for private review rather than posting it.

Acceptance and external release are separate. This skill never opens a channel,
publishes an artifact, schedules an update, or authorizes wider distribution.
